## Key question 1: What pixel scale (screen px per art px) reads as "fine" vs "chunky" on a 400-450 ppi phone, with examples from shipped pixel-art mobile games?

### Takeaway
Shipped pixel-art games put roughly 320-480 art pixels across the screen width (Celeste renders at 320x180 and integer-scales 6x to 1080p; Stardew draws 16-px tiles at 4x on a 64-px grid, i.e. about 480 art px across a 1920-px screen at 100% zoom), whereas PawPixel shows ~96-104 art px across a 1080-px phone (11x). Nobody publishes a "fine vs chunky" threshold in screen-px-per-art-px, but the practical rule from developer forums is "at least 4x so the pixels look intentional", and the physical size of a pixel block (ppi x scale) is what the eye reads as chunky.

### Inferences
- Arithmetic (mine): at 400 ppi one screen pixel is 25.4/400 = 0.0635 mm; at 450 ppi 0.056 mm. PawPixel's 11x block is therefore 0.62-0.70 mm wide; a 4x block would be 0.23-0.25 mm, 6x 0.34-0.38 mm. For comparison, Stardew at 4x on a 24" 1080p monitor (~92 ppi, 0.276 mm/px) draws 1.1 mm blocks, and Celeste at 6x on the same monitor 1.66 mm blocks. So PawPixel's blocks are physically smaller than desktop Stardew's; what makes them read as chunky is that only ~100 art pixels span the view, versus 320-480 in those games. "Fine" is mostly a function of art pixels per screen width (and per character), not of screen px per art px alone.
- Target that matches shipped practice: render the room at 2-3x the current source resolution (roughly 200-300 art px across the phone) and draw at 4-5x integer scale. Dead Cells' 3D-rendered sprites and Pokémon DS at 96x96 suggest a hero character of 64-96 source px tall is the norm when the character is the focus; PawPixel's pet at 34 px tall is at the small end (GBA/Gen I-III range).
- Stardew's separate Zoom Level and UI Scale settings imply the scene and the UI are drawn at different pixel sizes on purpose (see Q4).

## Key question 2 (part of cover item 2): Integer scaling, nearest-neighbour filtering, subpixel/camera alignment, and how Compose/Skia drawImage filterQuality and dstSize interact

### Takeaway
Compose's `DrawScope.drawImage` takes `dstOffset: IntOffset` and `dstSize: IntSize` in device pixels, so a scaled draw is always an integer number of device pixels, and `FilterQuality.None` is nearest-neighbour; the default is `FilterQuality.Low` = bilinear, which blurs. The engine-side rules (Unity Pixel Perfect Camera) are: fixed reference resolution, integer zoom, snap sprites to a 1/PPU grid, and no sub-pixel movement.

### Cited Findings
- Compose `FilterQuality` KDoc: `None` = "Fastest possible filtering, albeit also the lowest quality. Typically this implies nearest-neighbour filtering."; `Low` = "Typically this implies bilinear interpolation."; `Medium` = "a combination of bilinear interpolation and pyramidal parametric prefiltering (mipmaps)"; `High` = "bicubic interpolation or better." — [FilterQuality.kt, AndroidX source](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui-graphics/src/commonMain/kotlin/androidx/compose/ui/graphics/FilterQuality.kt)
- `DrawScope.drawImage(image, srcOffset: IntOffset = IntOffset.Zero, srcSize: IntSize = IntSize(image.width, image.height), dstOffset: IntOffset = IntOffset.Zero, dstSize: IntSize = srcSize, alpha, style, colorFilter, blendMode, filterQuality: FilterQuality = DefaultFilterQuality)`; `DefaultFilterQuality = FilterQuality.Low`, documented as "Maps to the default behavior of bilinear filtering"; `dstSize` is "Optional dimensions of the destination to draw, this defaults to [srcSize]"; `filterQuality` is the "Sampling algorithm applied to the [image] when it is scaled and drawn into the destination" — [DrawScope.kt, AndroidX source](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui-graphics/src/commonMain/kotlin/androidx/compose/ui/graphics/drawscope/DrawScope.kt)
- Android: `px = dp * (dpi / 160)`; density buckets mdpi ~160, hdpi ~240, xhdpi ~320, xxhdpi ~480, xxxhdpi ~640 with scale ratio 3:4:6:8:12:16; "Otherwise, Android must scale your bitmap ... resulting in scaling artifacts such as blurring"; resources the system must never scale go in `nodpi`; `inScaled = false` on a `Bitmap` disables pre-scaling — [Android "Support different pixel densities"](https://developer.android.com/training/multiscreen/screendensities)
- Unity Pixel Perfect Camera (docs, package versions 1.0-6.0): "Assets Pixels Per Unit ... Match this value to the Pixels Per Unit values of all Sprites in the Scene"; Reference Resolution is "the original resolution your assets are designed for. Scaling up scenes and assets from this resolution preserves your pixel art cleanly at higher resolutions"; "By default, the scene is rendered at the pixel perfect resolution closest to the full screen resolution"; Upscale Render Texture renders "to a temporary texture set as close as possible to the Reference Resolution ... then upscaled to fit the entire screen"; "Pixel Snapping ... snap Sprite Renderers to a grid in world space at render-time. The grid size is based on the Assets' Pixels Per Unit value ... prevents subpixel movement and make Sprites appear to move in pixel-by-pixel increments"; for movement, "Set the Move X/Y/Z properties to 1 divided by the Pixel Perfect Camera's Asset Pixels Per Unit (PPU) value"; "Crop Frame: Crops the viewport with black bars to match the Reference Resolution along the checked axis"; Stretch Fill "expand[s] the viewport to fit the screen resolution while maintaining the viewport's aspect ratio" (non-integer, filtered) — [2D Pixel Perfect manual 5.1](https://docs.unity3d.com/Packages/com.unity.2d.pixel-perfect@5.1/manual/index.html), [Unity 6.3 URP reference](https://docs.unity3d.com/Manual/urp/2d-pixelperfect-ref.html) (search snippets)
- Sub-pixel movement is a separate cause of uneven pixels: "the player will move with floating-point accuracy regardless of game resolution", and the fix is "restricting the sprite to whole coordinates" — [GDevelop forum](https://forum.gdevelop.io/t/pixel-perfect-is-not-pixel-perfect-in-fullscreen-mode/67927) (search snippet)
- A "pixel art looks bad on mobile" fix list: integer scaling makes the game area smaller (letterbox), disabling pixel rounding blurs — [Construct 2 forum](https://www.construct.net/en/forum/construct-2/how-do-i-18/pixel-art-game-looks-bad-73848) (search snippet)
- Local code (this repository): `LivePet.kt` already draws the room, props and pet with `FilterQuality.None` and an integer `px` (`pixelScale()` floors the ratio when >= 1, lines 363-366); the pet's per-depth scale is `petPx = (g.size(depth) * px).roundToInt()` (line 221) so it is also an integer; prop origins are `(p.x * px).roundToInt()` (line 212). The deliberate exceptions are the depth-of-field "softBand" copies drawn with `FilterQuality.Medium` (line 280). One place still uses a dp-derived, possibly fractional scale: line 381 `val pxDp = with(LocalDensity.current) { pixel.toPx() }` then `IntSize((cols * pxDp).roundToInt(), ...)` (line 390) — on a 2.625-density phone a dp-based pixel size is fractional, so columns come out alternately 10 and 11 device px wide. `DecorateScreen.kt` uses `px = floor(width / 100f).toInt()` (line 323), which is integer. — `/home/user/pawpix/composeApp/src/commonMain/kotlin/com/pawpixel/app/ui/LivePet.kt`, `/home/user/pawpix/composeApp/src/commonMain/kotlin/com/pawpixel/app/ui/DecorateScreen.kt`

### Inferences
- Concrete rendering rules for Compose on both platforms (derived from the sources above): (1) compute the scale in device pixels, never dp: `px = floor(availablePx / artWidth)`, minimum 1; (2) draw every bitmap with `dstSize = IntSize(w * px, h * px)` and `filterQuality = FilterQuality.None`; (3) round every origin to whole device px (`IntOffset`) and keep all art-space positions integral (floor the animator's x/y before multiplying by `px`), so a sprite never straddles a device pixel; (4) do not apply `Modifier.scale`, `graphicsLayer` scale, rotation or `Image(contentScale = Fit)` on top of a pixel-art bitmap (those resample with bilinear); (5) letterbox or extend the scene (draw more wall/floor rows, as `LivePet` already does with `rows = ceil(size.height / px)`) rather than stretching to fill; (6) if the composable is sized in dp, size the parent in dp but measure in px inside `BoxWithConstraints`, because 1 dp = 2.625 px on a 420-dpi phone and = 3 px on an iPhone (iOS `UIScreen.scale`) — the latter is my general knowledge, Apple's page body could not be read.
- Because `dstSize` is `IntSize`, a non-integer intended scale (e.g. 10.5x) is silently rounded to a whole pixel size for the whole image, and nearest-neighbour then distributes the remainder as alternating 10- and 11-px columns; this is the "uneven pixels" artefact and is why `floor` must be applied before, not after, multiplying.
- The pet's perspective scaling (`g.size(depth)`) changes `petPx` in integer steps as the pet walks between tile rows; that is correct pixel-art practice (pop between integer scales) and avoids the alternating-column artefact, at the cost of visible size steps.
- On iOS, Compose Multiplatform renders through Skia as well, so the same `FilterQuality.None` path applies; the native WidgetKit widget must do its own nearest-neighbour (`.interpolation(.none)` on a SwiftUI `Image`) — general knowledge, not from a fetched source.

### Gaps
- Apple's HIG page could not be read, so the @1x/@2x/@3x and `interpolation(.none)` details are unsourced here.
- Skia-level behaviour (whether `FilterQuality.None` maps to `SkFilterMode::kNearest` and how `dstSize` rounding is applied inside Skia) was not verified against Skia docs; the AndroidX KDoc is the only source.

## Key question 3 (cover item 3): Pixel-art upscaling algorithms — what each does, cost, where they look good/bad, and which upscaler would best turn a 41x34 cartoon pet into an 82x68

### Takeaway
Two families exist: palette-preserving pattern copiers (Eagle 1997-era, Scale2x/EPX 2001, Scale3x) that only copy neighbouring colours and smooth 45-degree stairs, and interpolating edge-aware scalers (2xSaI, hq2x/3x/4x, xBR, xBRZ, Super-xBR, OmniScale) that blend new colours along detected edges. For a clean-outlined cartoon sprite, hqx and xBR/xBRZ give the most "hand-drawn" result; EPX is the only one that is trivially ~30 lines and keeps the palette; all of them damage 1-px eyes/highlights and dithering, and emulator communities note that applying them per sprite chunk (not to the whole frame) gives suboptimal results.

### Cited Findings
- Scale2x/Scale3x/Scale4x (AdvMAME2x/3x/4x): "real-time graphics effects able to increase the size of small bitmaps guessing the missing pixels without blurring the images", "originally developed for the AdvanceMAME project in the year 2001" by Andrea Mazzoleni; the repo provides "fast C and SSE2 implementations"; "the implementation of the Scale4x effect is not obvious without using a big intermediate buffer" (it is Scale2x applied twice); the specification is at scale2x.it — [amadvance/scale2x README](https://github.com/amadvance/scale2x)
- The Scale2x rule (described in an academic paper, not the spec page): the centre pixel P and its four orthogonal neighbours A, B, C, D map to a 2x2 output; each quadrant copies one neighbour when two neighbours match and the other two differ, otherwise keeps P — [ITB paper on Scale2x](https://informatika.stei.itb.ac.id/~rinaldi.munir/Matdis/2009-2010/Makalah0910/MakalahStrukdis0910-013.pdf) (search snippet). Later Scale2xSFX/Scale3xSFX "provid[e] better diagonals rendering and less artifacts on some patterns" — [ScaleNx on PyPI](https://pypi.org/project/scalenx/) (search snippet). A ~100-line JavaScript EPX exists — [pixel-scale-epx on npm](https://npmjs.com/package/pixel-scale-epx)
- Eagle (Dirk Stevens): "a single black pixel on a white background will vanish under the Eagle algorithm", solved by EPX, 2xSaI and HQ2x — [Wikipedia "Pixel-art scaling algorithms" (blocked; via search snippet)](https://en.wikipedia.org/wiki/Pixel-art_scaling_algorithms)
- 2xSaI / Super 2xSaI / Super Eagle: by Derek Liauw Kie Fa ("Kreed"), GPL, "inspired by the Eagle engine", built for emulators (Gens, VisualBoyAdvance, Kega Fusion) — [Sega Retro "2xSaI"](https://segaretro.org/2xSaI) (search snippet); known artefacts: "black line artifacts along the top and bottom edges" in the original implementation and output "slightly shifted ... with dark edges along the bottom/right sides" — [paint.net plugin thread](https://forums.getpaint.net/topic/22560-pixel-art-scaling-plug-in-beta-release/), [ScummVM bug 3091549](https://lists.scummvm.org/pipermail/scummvm-tracker/2010-October/007383.html) (search snippets)
- hq2x/hq3x/hq4x (Maxim Stepin): analyses the 3x3 block around each pixel, marks each of the 8 neighbours "close" or "distant" by a YUV threshold (more tolerance on Y than U/V), giving 256 patterns; a 256-entry lookup table says how to blend source pixels; the table was built by "finding the most likely shape for each pattern, preserving edges, then rasterising it at 3x with anti-aliasing"; "suits images with clear, sharp edges, such as line graphics and cartoon sprites", "not designed for photographs"; "fast enough to process 256x256 images in real-time"; used in Nestopia, bsnes, ZSNES; LGPL-2.1 — [grom358/hqx README](https://github.com/grom358/hqx)
- xBR (Hyllian, "scale by rules"): "works by detecting edges and interpolating pixels along them", with "empirical rules developed to detect the edges in many directions"; shader "lvl2" detects four edge directions, "lvl3" six; xBR "works much like HQx, using pattern recognition, but adds a 2-stage set of interpolation rules, which better handle more complex patterns such as anti-aliased lines and curves"; "background textures keep the sharp characteristics of the original image, rather than becoming blurred like HQx"; "pure xBR and SABR are specialized in 2D flat images only"; Super-xBR "uses parts of the xBR algorithm and combines with other linear interpolation ones, and is aimed at games with smooth color gradients" — [libretro forum "xBR algorithm tutorial" (marked outdated by the author)](https://forums.libretro.com/t/xbr-algorithm-tutorial/123/21), [RetroArch xBR shader README](https://otakon273.duckdns.org/Consoles/RetroArch-Win64/shaders/shaders_slang/xbr/README.md) (search snippets)
- xBRZ (Zenju): "a modified approach of xBR" whose "rule set is designed to preserve small image features"; GPLv3; "highly optimized performance", multithreading, 64-bit, image slices; reference implementations in DOSBox, ePSXe, HqMAME, ScummVM, Snes9x, Kega Fusion; a "Scaler Test" tool to compare scalers on your own images — [xBRZ on SourceForge](https://sourceforge.net/projects/xbrz/); integer factors only, maximum 6 ("up to 6xBRZ") — [DOSBox-X xbrz.h](https://dosbox-x.com/doxygen/html/xbrz_8h_source.html), [xbrz-rs crate](https://docs.rs/xbrz-rs) (search snippets); a Java port is on Maven Central as `io.github.stanio:xbrz-core` — [Sonatype listing](https://central.sonatype.com/artifact/io.github.stanio/xbrz-core); a paint.net user describes it as trying "to intelligently determine the edges of a character's face or their eyes, or diagonal lines" — [paint.net xBRZ plugin thread](https://forums.getpaint.net/topic/117672-xbrz-upscaling-png-filetype-plugin-v202101166-16th-jan-21/) (search snippet); a 2026 paper says xBRZ "uses a complex set of pattern recognition rules to analyze the local neighborhood of each pixel and determine edge directionality, which is more involved than Scale2x's simple corner-rounding" — [MDPI Applied Sciences 16(5):2314](https://www.mdpi.com/2076-3417/16/5/2314) (search snippet)
- Zenju built xBRZ after deciding there was "a new far superior image scaling technique available than HQx" (author's own claim) — [Vogons thread, first post](https://www.vogons.org/viewtopic.php?p=287296) (search snippet)
- OmniScale (SameBoy, Lior Halphon): listed by SameBoy as an "exclusive algorithm" alongside "Anti-aliased Scale2x"; the SameBoy build "requires OpenGL 3.2 or later or Metal" (it is a GPU shader); a Godot port (MIT) describes it as "an emulator-style pixel upscaling algorithm" that "works similarly to hqx at arbitrary precision", i.e. non-integer factors — [SameBoy README on SlackBuilds](https://mirror.slackbuilds.org/slackbuilds/15.0/games/sameboy/README), [Godot asset "OmniScale"](https://godotengine.org/asset-library/asset/258) (search snippets)
- Classic scalers "are only capable for magnifying picture in predefined size, such as 2x, 3x, or 4x"; the usual workaround for other factors is to magnify with a fixed scaler then resample down with Lanczos — [ImageMagick forum](https://imagemagick.com/discourse-server/viewtopic.php?p=98080) (search snippet)
- On applying smoothing scalers to games deliberately: Beamdog's Infinity Engine 2.0 update "added an HQ-style filter to the characters" with a nearest/linear toggle (user report); Steam's Indiana Jones and the Last Crusade ships a smoothing filter users disagree is HQ2x; a TASVideos thread notes "running the smoothing algorithm on the individual sprite chunks would likely result in suboptimal results" — [Beamdog forum](https://forums.beamdog.com/discussion/comment/795951), [Steam thread](https://steamcommunity.com/app/32310/discussions/0/558752449978527209), [TASVideos "Depixelizing emulators"](https://tasvideos.org/Forum/Topics/18689) (search snippets)
- Dithering vs scalers: no direct test found; a non-authoritative guide recommends hq2x/hq4x "for complex gradients or dithering" and xBR "for maximum quality on hero assets", and to "test both" — [third-party skill page](https://claudskills.com/skills/pixel-art-scaler/SKILL.md) (search snippet; low authority)

### Inferences
- Implementation effort (my estimate from the algorithm descriptions): EPX/Scale2x is 4 comparisons and 4 writes per source pixel — about 30 lines of Kotlin over an `IntArray`, no new colours, so PawPixel's palette (`PetLook`) survives. Scale3x is ~60 lines (9 output pixels, 8-neighbour rules). Eagle is ~20 lines but loses isolated 1-px features (eye highlights), so it is unsuitable. 2xSaI is ~200 lines and has the documented edge-shift artefacts. hqx needs its 256-pattern table (the reference C is several thousand generated lines) and xBRZ is ~1000+ lines of C++; neither fits "100 lines", but xBRZ has a Java port usable from the JVM target and a Rust crate, and both are GPL/LGPL (licence matters for an app store build). OmniScale is a GPU shader, which does not fit a software `IntArray` pipeline.
- The EPX rule as I know it from the Scale2x specification (unverified here because scale2x.it was unreachable; verify before quoting): for centre P with up B, left D, right F, down H, output `E0 = (D==B && B!=F && D!=H) ? D : P; E1 = (B==F && B!=D && F!=H) ? F : P; E2 = (D==H && D!=B && H!=F) ? D : P; E3 = (H==F && D!=H && B!=F) ? F : P`.
- Expected artefacts on a 41x34 chibi going to 82x68: EPX/Scale3x turn every 45-degree stair into a clean diagonal but leave shallow slopes stair-stepped at 2x, round every outside corner by one pixel, and can "fill in" 1-px gaps between the outline and a 1-px eye highlight (the highlight stays, but single dark pixels next to a same-colour neighbour sprout diagonal spikes). hqx and xBRZ smooth the outline into an anti-aliased curve and round the eyes; because they interpolate, they introduce intermediate colours (bad for the flat 2-3-tone palette look, and the widget's mood PNGs grow in colour count), and checkerboard dithering (if `SpritePipeline` emits any) becomes streaky. Outline thickness becomes uneven: a 1-px outline is 2 px after any 2x scaler, with rounded corners thinner than 2 px.
- Best choice for the stated goal: because `Chibi` draws the pet procedurally from look + species + style, redrawing natively at 82x68 (double the canvas, 1-px outlines kept at 1 px, hand-placed AA) will beat any upscaler, since the scaler cannot know which 2x2 blocks were "one stroke". If a scaler must be used as a stopgap, Scale2x (then integer-scale the result 5-6x with nearest) is the one that keeps the palette and is cheap enough to run per frame on the phone; xBRZ 2x via the Java port is the one that will look most "hand-drawn" on the cartoon outlines, at the cost of new colours, a GPL dependency and no common-code (KMP) port. The authors' own guidance (hqx: "line graphics and cartoon sprites"; xBR: "2D flat images") says a flat-shaded chibi is exactly the input these scalers were designed for.
- No evidence that any well-known pixel-art mobile game ships these scalers deliberately; emulators and remaster ports (Beamdog) are the documented users.

### Gaps
- Wikipedia's algorithm table, the Scale2x specification, Hyllian's tutorial text, Zenju's Vogons description, Janert's 2022 "A Comparison of Pixel-Art Scalers" (https://janert.me/blog/2022/pixel-art-scalers/), and Kopf-Lischinski "Depixelizing Pixel Art" (https://johanneskopf.de/publications/pixelart/) could not be fetched; the exact rule sets, per-factor behaviour of xBRZ 3x-6x, RotSprite, and the Kopf-Lischinski vector method are therefore not described from primary text.
- No source directly tests any scaler on dithered sprites or on 1-px eyes; the artefact list above is inference from how the algorithms work.

## Key question 4 (cover item 4): "Mixels" — should UI icons, scene and sprite share one pixel size, and how do Stardew / ACNH / Unpacking handle UI vs scene pixel size?

### Takeaway
The pixel-art community rule is that everything on screen should sit on one grid with one outline thickness ("no mixels"), with backgrounds as the only tolerated exception, but shipped games break it: Stardew exposes separate Zoom Level and UI Scale settings, so its UI and scene pixels are different sizes by design. ACNH is not pixel art and Unpacking's UI handling is not documented in anything reachable.

### Cited Findings
- Mixels: "a pixel of incoherent or inconsistent size when compared to the rest of the artwork as a whole" — [ozdic.com "mixel"](https://ozdic.com/word/mixel) (search snippet); the practice is "changing the pixel size for certain parts or just in the art" (e.g. from size 3 to 2); "the only place for it is backgrounds, and ... you still can't change the pixel size within the background" — [Flowlab community, "Mini rant: stop using mixels"](https://community.flowlab.io/t/mini-rant-stop-using-mixels/38287) (search snippet)
- Citing Michael Azzi's book Pixel Logic: "all the pixel art should fit on the same 'grid'" and "the outlines of the pixel art should have the exact same thickness" — [itch.io comment](https://itch.io/post/8448610) (search snippet)
- Mixels commonly arise "when an artist scales up their work, then continues drawing on it with a 1 pixel brush"; "some artists use mixels on purpose for a modern look"; scale by whole-number multiples, not fractions like 150% — [search-summarised source](https://blog.usesession.com/tag/pixel-art?page=23) (search snippet)
- Stardew: Zoom Level (75%-200%) and UI Scale are independent options; the modder guide tells modders to test with "zoom to maximum and UI scale to minimum" — [Stardew modder guide](https://wiki.stardewvalley.net/Modding:Modder_Guide/Game_Fundamentals) (search snippet); on ultrawide PC, UI/Zoom at 75-80% cut off the screen edge — [Stardew forums](https://forums.stardewvalley.net/threads/bug-ultrawide-resolution-ui-scale-zoom-level-display-issue.3121) (search snippet)
- Unpacking's art direction started from "what is the smallest item she can make in pixel art that is still recognizable", shrinking a mug until it felt right — [Sifter interview with Wren Brier and Tim Dawson](https://sifter.com.au/post/unpacking-is-an-indie-puzzler-with-heart-and-a-personal-story-for-developers-wren-and-tim) (search snippet)
- UI asset packs aimed at cozy games advertise icons "optimized for 16x16 grid" and 9-slice panels so borders stay crisp when resized — [itch.io tool UI pack](https://biruk-okami.itch.io/tool-ui-pack-pixel-art-icons-toolbar), [Unreal forum Indigolay pack](https://forums.unrealengine.com/t/indigolay-pixel-hud-dialogue-ui-pack-daily-life/2744350) (search snippets)

### Inferences
- A practical compromise consistent with both the rule and Stardew's practice: keep one pixel size inside the diorama (room, props, pet, shadow), and let the chrome (buttons, text, icons) use a different, usually smaller, pixel size or non-pixel vector UI, as long as the UI's own elements share one grid among themselves. Mixing pixel sizes within the diorama (e.g. a 2x-scaled pet on a 1x room) is what reads as "mixels".
- Pixel-art UI at the scene's 11x scale would be unusably coarse for text; this is the same pressure that made Stardew expose UI Scale separately.

### Gaps
- Lospec's own terminology page and Pixel Logic itself were not reachable; the Azzi quote is second-hand.
- No source on how Unpacking sizes its UI relative to its items, and ACNH is a 3D game (no pixel grid), so there is nothing to report for it.

## Key question 5 (cover item 5): Source resolution for a phone-filling character and the outline / anti-aliasing / selout / cluster rules that make pixel art read as fine rather than blocky

### Takeaway
Character references cluster at 64x64 (GBA Pokémon) to 96x96 (DS Pokémon) source pixels when the character fills the view, and tile-based characters at 1x2 tiles with the head one third to one half of the sprite; the craft rules are 1-px lines whose segments connect only diagonally (no "doubles"), even stair lengths (no "jaggies"), hand-placed anti-aliasing in corners with few shades, and selective outlines whose colour follows the lighting instead of flat black.

### Cited Findings
- Common sprite size is 1 tile wide by 2 tiles tall; at small sizes the head takes up a third to half of the total sprite — [Slynyrd, Pixelblog 22 "Top Down Character Sprites"](https://www.slynyrd.com/blog/2019/10/21/pixelblog-22-top-down-character-sprites) (search snippet)
- Generic size guidance from asset guides: 16x16 for props/items/icons, 32x32 for characters in top-down and platformers, 48x48 to 64x64 for detailed characters and bosses — [Wayline "Pixel Art for Games" lesson 1](https://www.wayline.io/learn/pixel-art/0), [pixnote resolution guide](https://pixnote.net/en/learn/resolution) (search snippets; secondary)
- Pokémon: 64x64 (Gen III), 96x96 (Gen IV-V, forum-sourced), 40-56 px (Gen I-II) — see Q1 citations
- "The most basic line in pixel art is a single pixel wide", and "the trick is to make the segments of the line only connect diagonally"; outlines "help separate objects from the background, as well as other objects" — [Lospec, "Pixel Art Outlines" by skeddles](https://lospec.com/articles/pixel-art-outlines) (search snippet)
- Selout (selective outlining) "replaces pure black outlines around sprites": "where the sprite is darkest, a dark colour is used for the outline, and where it's lightest a lighter colour is used", keeping outline-to-object contrast consistent all round; simplest form is "an outline that's a darker shade of the object it outlines"; check outlines against the background colour — [Lospec, "Pixel Art Outlines part 2: using color"](https://lospec.com/articles/pixel-art-outlines-part-2-using-color), [imonk "Selective Outlines" tutorial](https://itch.io/t/2422252/pixel-tutorial-selective-outlines) (search snippets)
- "Doubles" are two stacked pixels that thicken a 1-px line and interrupt its flow; "jaggies" are uneven step lengths that break an otherwise smooth curve; fix by walking the outline and evening out the stair-steps so each run is a consistent length — [Wayline lesson 2](https://www.wayline.io/learn/pixel-art/1) (search snippet)
- "In doing pixel and sprite art, you assume that your lines are usually 1 pixel in width"; where a line partly covers a pixel, "the final color gets mixed towards the color of the line by exact fraction of how much the line covers the pixel" — [Wesnoth wiki, "How to anti-alias sprite art"](https://wiki.wesnoth.org/How_to_anti-alias_sprite_art) (search snippet)
- "The key to anti-aliasing is place the mid-tone pixels in corners, and to keep them spaced away from each other"; "when creating strict Pixel Art, it is essential that you are not using any tool that creates Automatic Anti-Aliasing"; AA "has to be applied judiciously and by hand" — [Tiny Warrior Games, "Pixel Art Anti-Aliasing"](https://tinywarriorgames.com/2018/12/14/game-development-pixel-art-anti-aliasing/), [DeviantArt "Anti-Aliasing Manual vs Automatic"](https://www.deviantart.com/clefairykid/journal/Anti-Aliasing-Manual-VS-Automatic-358906411) (search snippets)
- Pixel Parmesan's "Anti-Aliasing Fundamentals for Pixel Artists" exists at [pixelparmesan.com](https://pixelparmesan.com/anti-aliasing-fundamentals-for-pixel-artists) but could not be read.

### Inferences
- For a phone-filling chibi: a 64-96 px tall character at 4-5x integer scale gives 256-480 device px of character on a 1080-wide phone, which is the range shipped games use; PawPixel's 34-px-tall pet at 11x is 374 device px tall, so the on-screen size is already right and only the source density is low. Doubling the canvas to 82x68 (drawn natively, with the extra rows for rabbits kept proportional) and halving the scale to 5-6x is the smallest change that moves it into that range; tripling (123x102 at 3-4x) matches Pokémon DS density.
- At 2x source density, the rules above become applicable in a way they cannot be at 41x34: the outline stays 1 px (so it is 5-6 device px instead of 11), eyes can be 2-3 px with a 1-px highlight, AA pixels can be placed on the outline corners, and selout can replace flat dark outlines, all of which make the art "read fine". A scaler cannot add these because it does not know the stroke structure; the procedural `Chibi` drawer does.
- Cluster size: none of the reachable sources gave a numeric rule; the community rule implicit in "doubles/jaggies" is that a line is 1 px and a shading cluster should be larger than 1 px unless it is a deliberate highlight (inference).

- No source gives a numeric "cluster size" rule or a ppi-based threshold for when AA becomes visible.
